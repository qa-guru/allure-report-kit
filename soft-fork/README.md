# Soft-fork — UI slice of Allure 3

Not a fork of `allure-framework/allure3`. Only the UI slice is forked; the
engine (`core`, `reader`, `charts-api`, `web-commons`) stays a pinned upstream
dependency.

Built and working — see `../e2e` for a report generated by it.

| Package | Upstream | Kit |
|---------|----------|-----|
| plugin (Awesome) | `@allurereport/plugin-awesome` | `packages/plugin-awesome` → `@qa-guru/allure-report-kit-awesome` |
| plugin (Dashboard) | `@allurereport/plugin-dashboard` | `packages/plugin-dashboard` → `@qa-guru/allure-report-kit-dashboard` |
| web bundle (Awesome) | `@allurereport/web-awesome` | `packages/web-awesome` |
| web bundle (Dashboard) | `@allurereport/web-dashboard` | `packages/web-dashboard` |
| shared plugin machinery | — | `packages/plugin-core` |
| engine | `core`, `reader`, `charts-api`, `web-commons`, `web-components` | upstream, pinned to 3.13.x |

`withKit({ softFork: true })` rewrites `plugins.awesome.import` and
`plugins.dashboard.import` to the kit plugins. An explicit `import` set by the
user is never overwritten.

Both plugin packages are a dozen lines: everything they do lives in
`plugin-core`, parameterised by which upstream plugin to delegate to and which
forked bundle to load.

## The delta

Four files differ from upstream in each web bundle. Everything else is upstream
code, and everything that is not JSX glue lives in the kit package
(`@qa-guru/allure-report-kit/allure`), shared by both forks.

### 1. The seam — `Charts/index.tsx` (Awesome) · `Dashboard/index.tsx` (Dashboard)

Upstream dispatches chart data to a widget with a 13-case `switch`
(`getChartWidgetByType`). That function is untouched: it moved to
`stockWidgets.tsx` and is now the `stock` renderer path. Around it the fork adds
a registry lookup, so a tile can name its backend and kit panels — which Allure
skips as unknown chart types — get a place in the grid.

The manifest arrives as `window.allureReportKit`, injected by the plugin.

### 2. `stockWidgets.tsx` — upstream's switch, moved verbatim

Not edited, only relocated, so the sync diff stays honest.

### 3. `src/index.tsx` — two lines

Mounts `theme.header` once for the whole app (report chrome, unlike the tile bar
which is card chrome) and pulls the kit theme into the entry bundle rather than
a lazy chunk, so the header offset applies on every section.

### 4. `src/assets/scss/index.scss` — a build fix, not a feature

Upstream imports design tokens from a sibling package by relative path
(`../../../../web-components/src/...`), which only resolves inside the allure3
monorepo. The published `@allurereport/web-components` ships `dist` only, and
the same tokens are already in its compiled `index.css`. See the file header.

## How the plugin swaps the bundle

`plugin-awesome` resolves its web assets through
`require.resolve("@allurereport/web-awesome/dist/...")`, so the bundle cannot be
swapped by configuration. Rather than copying the plugin's compiled source, the
kit plugin wraps it and proxies `context.reportFiles`:

- upstream bundle assets (everything in the upstream manifest) are dropped;
- `index.html` is retagged in flight — upstream's `<script>`/`<link>` out, the
  fork's in, plus `window.allureReportKit` and the backend globals;
- kit assets are written afterwards through the same interface.

No file is read back from disk and no report DOM is scraped, which is exactly
what separates this from the `dashboard-overrides.js` approach it replaces.

## Chart backends are not bundled

The fork ships no chart library. The plugin copies the UMD build of each backend
the config actually uses **from the consumer's `node_modules`** into
`kit/<id>.js` and adds a script tag; the runtime picks them up off `window`.

That keeps ECharts out of the bundle for reports that do not use it, and — more
importantly — means the kit never redistributes Highcharts or amCharts. The
consumer installs those under their own licence.

## Type checking

Asymmetric, and worth knowing before trusting a green build:

- **`web-dashboard`** type-checks. Its `moduleResolution` was bumped from `node`
  to `bundler` (a fork delta) so the checker can see the kit's `exports`
  subpaths; with that, upstream's source is clean.
- **`web-awesome`** does not. Upstream's `tsconfig.json` references a
  `tsconfig.node.json` for its vitest setup, which turns the config into a
  solution config and leaves `fork-ts-checker` inert — a deliberate `const x:
  number = "s"` compiles without a word. Dropping the reference surfaces **82
  pre-existing upstream errors** (missing `types` path alias, `preact/compat`
  typings, implicit `any`): that source never type-checked outside the allure3
  monorepo. The fork keeps upstream's config rather than pretending otherwise.

So the Awesome delta is verified by the build and the e2e smoke, not by `tsc`.
Making it checkable is a PLAN-0.1 item.

## Build

```bash
npm --prefix packages/web-awesome install
npm --prefix packages/web-dashboard install
npm run build:fork          # both bundles → dist/multi
npm --prefix e2e install
npm --prefix e2e run report # real reports at e2e/allure-report/{awesome,dashboard}
```

`dist/` is gitignored: a fresh clone builds the bundles.

## Upstream sync

Pinned at `@allurereport/* 3.13.x` (shipped by `allure@3.14.3`).

1. Diff the four delta files above against the new upstream `src`; everything
   else can be replaced wholesale.
2. Re-check `ChartType` in `charts-api`: a new member means a new `toChartModel`
   branch, not a new switch case.
3. Re-check the upstream `dist/multi/manifest.json` shape — the plugin drops
   assets by matching it.
4. `npm run sync:ds` in the kit — design-system primitives may have moved.
5. `npm run verify` (unit + dogfood) and `npm run verify:report` (real report).

## Not done yet

- `singleFile: true` — the plugins fall back to stock Allure and say so.
- Two theme switches (the DS header's and Allure's own) work independently.
- `web-awesome` is not type-checked (see above).
- Two upstream console defects the smoke filters out explicitly, both measured
  rather than assumed: the dashboard template links `favicon.ico` and never
  writes it, and upstream's nivo widgets emit negative SVG dimensions on this
  grid (same page: all-kit → 0 errors, all-stock → 8).
- Publishing: the packages resolve through `file:` links, nothing is on npm.
